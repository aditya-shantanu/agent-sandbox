# PR title: fix(sandboxclaim): suppress stale-pass writes; bounded requeue on adoption conflicts
Branch: aditya-shantanu:upstream-p4-claim-write-suppression

#### What this PR does / why we need it:

This PR re-expresses two write-path invariants on top of #1118's same-pass
adoption finalization (it deliberately does NOT reintroduce the deferral
machinery #1118 removed — no sentinel-driven polling of every adoption, no
`AdoptionPending` condition, no early-return status guard):

**1. A stale-view reconcile pass performs zero writes.** After the claim
controller commits a binding (warm adoption or cold create) and persists the
bound status, later passes can still read cache views that predate those
writes — queued requests, watch-event reordering across the claim and sandbox
informers, or a requeue racing the cache. Today such a pass re-runs the
adoption patch (the "one idempotent re-patch" #1118 accepted), or worse:
a pass whose *claim* view predates the binding re-enters candidate adoption
(burning a warm candidate on an optimistically locked claim update that can
only 409), falls through to a cold-path create when the warm queue is
momentarily empty, re-sends a byte-identical status patch (each one spawning
another watch event and another redundant pass), and re-records the
Ready-transition latency histograms — the #940 duplicate-observation bug,
which corrupts every histogram-derived quantile.

The mechanism is a per-claim-UID in-memory record of the last status this
controller instance successfully persisted (refreshed from the status-patch
server response), mirroring the existing `observedTimes` map in lifecycle and
eviction. Because the record is only stored after a successful status write, a
claim view carrying no binding while a record exists can only predate the
committed transition — so the pass bails with a nil error and a bounded 50ms
backstop requeue before any write. Convergence stays event-driven, exactly as
#1118 argued: the committed writes each produce a watch event that re-enqueues
the claim. After a controller restart the record is empty and stale passes
degrade to precisely #1118's idempotent re-patch behavior (still covered by
the existing restart-path test).

**2. Adoption conflicts get a bounded requeue, not exponential backoff.** A
409 on the optimistically locked claim update that records an adoption
currently propagates as a reconcile error and routes through
controller-runtime's per-item exponential backoff (5ms·2^k). Measured in a
300-claim warm-adoption benchmark, this produced visible retry waves at
0.8/1.2/1.6s: losing a race once pushed a claim's latency out by whole backoff
steps, and the waves re-synchronized the herd so the retries collided again.
The conflict is now converted to a nil error with a 50ms `RequeueAfter`; the
popped warm candidate was already returned to the queue before the conflict
surfaced, so the retry pass has a fresh candidate immediately. This follows
the precedent of PR #1072 (bounded requeue instead of failure backoff for
benign races, #1042).

Evidence, measured in a 300-claim warm-adoption benchmark on the fork this is
extracted from: the pre-fix controller executed 4,357 reconciles for 300
claims; ~45% of adoption writes ended in 409 conflicts; 144 duplicate
cold-path sandboxes were created and thrown away; and the startup-latency
histograms recorded 911 observations for 300 claims (the #940 bug). With the
stale-pass guard, stale passes performed zero writes (521 suppressed per
burst) and adoption conflicts fell to ~0 — leaving the bounded conflict
requeue as a rarely-exercised graceful floor. That data also suggests the
right fix for conflict-driven latency is removing the doomed writes and
bounding the retry, rather than exposing a per-CRD retry/backoff knob as
proposed in #1059.

Both changes are unconditional (no flag): suppressing writes that can only be
redundant or doomed has no trade-off, and the restart path preserves today's
semantics.

Unit tests pin the invariants following the existing cache-lag test
conventions:
- interceptor-counted (every write verb) proof that stale passes are
  write-free on both entry paths: the annotation-recovery path with a frozen
  warm-pool-owned sandbox view, and a frozen pre-adoption claim view at the
  adoption/cold entry — including a drained-queue pass proving no cold-path
  create (`TestSandboxClaimStaleViewSuppressesAdoptionRepatch`,
  `TestSandboxClaimStalePreAdoptionViewPerformsZeroWrites`);
- histogram sample-count assertions (not series counts) that a stale pre-Ready
  view neither re-records `ClaimStartupLatency` nor re-sends the
  byte-identical status patch
  (`TestSandboxClaimStaleViewSuppressesDuplicateReadyMetric`, plus a
  `recordCreationLatencyMetric` table case);
- an adoption 409 yields nil error + `RequeueAfter=50ms`, the candidate is
  back in the queue, and the surfaced condition is a benign
  `AdoptionConflict` (`TestSandboxClaimAdoptionConflictBoundedRequeue`);
- restart degradation (empty in-memory record → idempotent re-patch, status
  never wiped) remains covered by
  `TestSandboxClaimAdoptionCacheLagPreservesFinalizedStatus`, and the
  duplicate-adoption invariant by
  `TestSandboxClaimPreventsDuplicateAdoptionDuringCacheLag`.

#### Which issue(s) this PR is related to:

Ref #527, Ref #940 (the duplicate histogram observations are the direct fix),
Ref #418 (stale passes re-entering adoption are the setup for double-adoption
races; the complementary optimistic lock on the sandbox-side adoption patch is
intentionally left to a follow-up), Ref #1042 — this extends PR #1072's
bounded-requeue-for-benign-races pattern to the claim adoption path, and the
measured data (conflicts ~0 once stale writes are suppressed) argues against
adding the per-CRD retry knob proposed in #1059.

#### Release Note

```release-note
SandboxClaim reconcile passes that read a cache view older than an already-committed adoption or cold-start transition no longer perform writes (no redundant adoption re-patch, no duplicate cold-path sandbox, no duplicate status patch, no duplicate startup-latency histogram records), and a 409 on the optimistically locked adoption write now retries via a bounded 50ms requeue instead of exponential backoff, with the warm candidate returned to the queue immediately.
```

## A/B protocol (deferred — run before filing this PR)

Single kops GCP cluster, reused for BASE and candidate legs; the A/B isolates
the code change, not the cluster. Full learned cluster configuration, applied
IDENTICALLY to both legs:

- Cluster: NODE_COUNT=6 workers, n2-standard-8 (e2-standard-8 if N2 quota is
  tight), NODE_VOLUME_SIZE=100, control plane n2-standard-16 — may fall back
  to e2-standard-16 under N2 quota pressure, identical on both legs.
- TUNE_CONTROL_PLANE=true: apiserver inflight raises; kube-scheduler client
  QPS 800/1600 via the cluster-yaml patch mechanism (kops v1.35 `--set` on
  `kubeScheduler.kubeAPIQPS` is silently inert — the round-10 cluster-spec
  patch mechanism is required); etcd quota-backend-bytes=8GiB + 2m periodic
  auto-compaction on both main and events clusters (etcdClusters[*].manager.env).
- TUNE_NODES=true: kube-apiserver eventTTL=15m, kubelet system reserves,
  100GB pd-ssd worker boot disks.
- CNI cilium with the enablePrometheusMetrics raise (creation-time).
- Clean instrumentation: stock logging, no --enable-pprof-debug, no zap debug
  level, no -v, no in-burst profiling on measurement legs.
- Harness: 300-claim warm-adoption burst (claims-warm phase),
  STRESS_SMOKE_COUNT=20 smoke gate before each full burst,
  --client-connections=4, harness capacity-math validation on; identical
  harness build drives every leg.
- Controller args on BOTH legs: --leader-elect=true --enable-webhook=false
  --sandbox-concurrent-workers=400 --sandbox-claim-concurrent-workers=400.
  No leg-specific flags: the change is unconditional, so CONTROLLER_ARGS are
  otherwise EMPTY on both legs and there is no flag leg.
- BASE leg: bench-wave2-base2 image (post-#1118 upstream/main 16e4aeb + the
  fork stress-harness overlay, bench-only commit).
- Change leg: bench-wave2-p4 image (upstream-p4-claim-write-suppression + the
  same overlay commit) on the identically tuned cluster.
- Teardown: kops delete cluster + verified deletion (poll `kops get cluster`
  until absent; assert zero leftover GCE instances).
- Report per leg: claim create->Ready p50/p90/p99 + time-to-all-ready, from
  the same harness build; additionally claim-controller reconcile count,
  adoption 409 count, cold-start count, and startup-latency histogram
  observation count vs claims completed (must be exactly 1:1 on the change
  leg — the #940 signal).
