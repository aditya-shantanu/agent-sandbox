## Findings (ordered by embarrassment potential)

### GAP-1 — Every headline number includes instrumentation tax; a "clean" leg has never been run
**Evidence:** the standard invocation (INFRASTRUCTURE.md §Standard invocation, RESULTS header) runs every leg — including the 584ms round-4/5 headline and the 31-40ms smoke floor — with `--zap-log-level=debug --zap-encoder=json --enable-pprof-debug`. `--enable-pprof-debug` sets `runtime.SetBlockProfileRate(1000000)` (~1ms sampling of **every** blocking event) and `SetMutexProfileFraction(10)` process-wide for the whole run (`cmd/agent-sandbox-controller/main.go:123-131, 316-318`), not just while a profile is fetched. Round-4 itself measured ~2,100 log lines/s at burst peak; debug JSON encode + block/mutex accounting sit inside every reconcile and every write RTT we reported. Instrumented legs additionally run the apiserver at `-v=3` (`run:163-166,242-244`).
**Why it matters:** at the 5.5s-baseline era this was noise; at a <100ms p90 target and a 31-40ms "physics floor," tens of ms of self-inflicted overhead is a first-order term — and the ROUND7 §7 stopping rule compares against a floor measured *with* the tax. Production (no debug flags) may already be faster than reported; alternatively the floor is lower than stated.
**Impact class:** validity + latency-p50/p90 at all rates. **Effort:** S (one A/B pair: stock logging, no pprof-debug, no `-v=3`).
**ROUND7 ordering:** **changes gate zero** — §3 must include a clean-instrumentation leg, or every §4 saving is measured against a polluted anchor and the §7 stopping rule can fire early/late.

### GAP-2 — The controller pod is BestEffort, unpinned, single-replica; bench placement is uncontrolled run-to-run
**Evidence:** `k8s/controller.yaml:93-126` (and helm `values.yaml:52` `resources: {}`): no `resources`, no `priorityClassName`, no nodeSelector/affinity, no PDB, `replicas: 1`. The controller therefore runs **BestEffort QoS**: minimal CPU weight under node contention, first eviction candidate under node pressure — on bench clusters it lands on a random one of the 6 workers, co-resident with churning sandbox pods (the GKE CL2 reference explicitly used a dedicated e2-standard-32 controller node; our A/Bs never controlled this variable). With no CPU limit, Go 1.26's container-aware GOMAXPROCS defaulting is also moot (GOMAXPROCS = 8 node cores).
**Why it matters:** at 300/s a refill storm on the controller's node steals CPU from the latency-critical process with zero reservation; at 1000/s (110-pod nodes, kubelet/cilium contention — the exact SCALING-GUIDE idea-B scenario, which protects *system daemons* but not our controller) this is a structural tail source and an availability hazard (BestEffort eviction of the only replica = GAP-9's recovery path). It is also uncontrolled variance inside every published A/B.
**Impact class:** tail + robustness + validity. **Effort:** S (requests/limits + priorityClass `system-cluster-critical` + bench nodeSelector or dedicated IG; record landing node per run).
**ROUND7 ordering:** joins gate zero as a prerequisite (same reason as GAP-1).

### GAP-3 — The deletion/teardown path has never been profiled — and round-2 already measured waste on it that no round remediated
**Evidence:** ROUND2-FINDINGS leg-B forensics recorded **1,629 teardown 404-PATCHes and 3,677 post-bind requeues** — measured once, never root-caused, absent from ROUND6's ledger, ROUND7's items, and the dead-end list. The teardown design itself was never examined: no finalizers on any of our CRDs (good — verified, only RBAC markers exist), so deletion is claim DELETE → KCM GC → sandbox DELETE → KCM GC → pod/child DELETE (two GC hops; KCM QPS is at least raised by TUNE_CONTROL_PLANE). Expiry adds uncounted writes: expired claim = +1 status PATCH (Expired condition) + event + DELETE (`sandboxclaim_controller.go:548-585`); expired sandbox = +1 status PATCH + child deletes + optional self-delete (`sandbox_controller.go:274-295, 1474-1546`). Claims/pools created together with identical TTLs expire together → a **synchronized teardown burst** competing with concurrent adoptions — the exact self-interference shape rounds 1-3 fought on the create side, unexamined on the delete side. A claim deleted mid-adoption also silently burns a warm candidate (reconcile aborts on DeletionTimestamp at `:522` but the in-flight adoption patch still lands; sandbox orphaned until GC).
**Why it matters:** at sustained rate, deletes ≈ creates by definition (the sustained phase's dwell→delete loop, `test/stress/sustained.go:272-306`, will generate them) — at 1000/s that's ~1000 claim DELETEs/s + cascades sharing APF seats with adoption. The 404-PATCH class alone, if it scales with teardown rate, is hundreds of wasted mutating requests/s. Controller-side deletes ride the **bulk** PL (apf-insulation catch-rest) but *client* claim DELETEs in production ride the tenant's PL — never modeled.
**Impact class:** churn + tail at 500-1000/s; robustness (expiry waves). **Effort:** S to instrument (teardown segment decomposition + per-write attribution in the sustained phase; adopt PR #882's `agent_sandbox_writes_total` here), S-M to fix the 404-PATCH waste (skip patches when `DeletionTimestamp != nil` — the sandbox controller only checks it at reconcile entry, `sandbox_controller.go:250`, not on the pod-patch path against cached pods already deleted server-side).
**ROUND7 ordering:** attach the measurement to gate zero's sustained phase (free ride); the waste fix slots beside item 5 hygiene. Add "teardown interference A/B" (sustained adoptions with/without concurrent 300/s expiry wave) to item 8's phase list.

### GAP-4 — Warm-pool scale-down and stale-member deletion can delete a just-adopted sandbox (no delete-time precondition); template-rollout deletions are unshaped
**Evidence:** `deletePoolSandbox` issues `r.Delete(ctx, sb)` with **no UID/resourceVersion precondition and no delete-time ownership recheck** (`sandboxwarmpool_controller.go:698-703`); excess/stale selection is computed from the informer cache (`:454-480`, stale-member deletes `:553`, stuck-sandbox deletes `:360`). Between the cache read and the DELETE, a claim's optimistic-lock adoption patch can win ownership — DELETE by name then kills the claim's just-bound sandbox. This is the mirror image of issue #418 (two-actors-one-sandbox), on the **delete** side, and the adoption optimistic lock does not protect against it because DELETE ignores ownerRef changes. Separately: pool scale-down and template-hash-stale replacement delete up to `maxBatchSize=300` members per pass via `slowStartBatch` with **no rate shaping** — `--sandbox-warm-pool-max-refill-rate` shapes creates only. A template update mid-traffic therefore triggers an unshaped delete storm + refill storm simultaneously (compounding #1182's fan-out, which only covers the re-reconcile side).
**Why it matters:** at 300/s the window is narrow but the failure is user-visible (Ready claim whose sandbox vanishes); at 1000/s with dynamic pool resizing and template rollouts the race window is hit routinely, and the unshaped delete+recreate burst is a self-DoS in the middle of traffic.
**Impact class:** robustness (correctness-grade) + churn. **Effort:** S — `client.Preconditions{UID:...}` plus RV-precondition delete (`DeleteOptions.Preconditions.ResourceVersion` from the cached copy: adoption bumps RV → delete fails 409 → re-list), + route pool deletions through the same token bucket as refill.
**ROUND7 ordering:** the precondition fix is correctness — do it with item-1 rebase work (same files upstream churns). Rollout shaping joins item 8.

### GAP-5 — The production read path was never load-modeled: SDK per-claim watches are structurally expensive and the bench cannot see it
**Evidence:** `wait_for_claim_ready` opens a **fresh watch per claim** with `field_selector=metadata.name=<claim>` and **no resourceVersion** (`clients/python/agentic-sandbox-client/k8s_agent_sandbox/k8s_helper.py:139-147`; async variant same). Consequences at rate: (a) a watch with unset RV requires the apiserver to establish initial state with a quorum etcd read (bypassing the watch cache) per wait; (b) CR watch caches have no trigger index, so every claim event is filter-evaluated against **every** open watcher — O(events × watchers); at 1000 claims/s with ~0.5s waits that is ~500 concurrent watchers × ~2-3k claim events/s ≈ 10⁶ filter evals/s plus per-watcher goroutine/buffer overhead and watch setup/teardown churn at 1000 conn/s. The stress client uses **one shared watch stream** for all claims (the `watch.jsonl` design), so every benchmark ever run models a read load shape production will not have. ROUND7 item 5(a) says "keep watcher count minimal" for the *controller* — the SDK is the violation, and it's unmeasured.
**Why it matters:** invisible at 300-burst benches; at 500-1000/s it is apiserver CPU + etcd read load competing with the write path we spent six rounds protecting.
**Impact class:** churn/apiserver-CPU at rate + latency-tail (watch-init RTT is in every client's observed create→Ready). **Effort:** S — SDK: watch from the create response's `resourceVersion` (or `resource_version="0"`), reuse a session-level watch for multi-claim clients; bench: add one leg with N per-claim watchers to quantify. Composes with #1089 idempotent-create work.
**ROUND7 ordering:** merge into item 9 (SDK guidance) — item 9 currently covers only arrival shaping and retries; this adds the read side.

### GAP-6 — Cold-start latency itself was never decomposed; every round made cold starts rare, none made them fast
**Evidence:** since round 2, "cold pod creation (~3-6s)" is a single opaque number (RESULTS candidate1 anomaly note); zero forensics on where those seconds go (scheduling vs cilium endpoint vs image pull vs containerd vs kubelet status writes vs our two controller passes). The pod template has no readiness probes (`test/stress/phases.go:buildSandboxObject` — verified: image + IfNotPresent only), no PriorityClass; nothing pre-pulls template images onto **new** (autoscaled) nodes — bench nodes get pre-pull as a side effect of pool fill, production scale-up nodes pay a full pull inside a user-visible cold start.
**Why it matters:** the cold path is the p99/max whenever the pool misses — and, more importantly, **refill latency = cold-start latency**, which sits directly in the pool-sizing formula (`replicas ≥ rate × (refill_p99 + hold)`, R4.6): cutting pod-start 4s→1.5s cuts required warm capacity ~2.5× at 1000/s — a capacity-dollars lever no latency round touches. justinsb's #1203-#1208 (ROUND7 item 8a) attack node I/O *throughput* under churn; single-pod cold **latency** levers are disjoint: image pre-pull DaemonSet / secondary-boot-disk images, `maxParallelImagePulls`/`--serialize-image-pulls=false`, PriorityClass tiering (claim-driven cold pods > refill pods, so the scheduler orders them under contention — complements #1214 preemption without overlapping it), cilium endpoint latency at the tuned limiter.
**Impact class:** tail (pool-miss) + churn-capacity at 500-1000/s. **Effort:** S to instrument (cold-start segment timing line mirroring the adoption one), M for levers.
**ROUND7 ordering:** no change to latency items; add as item 8(g) with the decomposition as its own gate.

### GAP-7 — The Go runtime is entirely unmanaged: no GOGC/GOMEMLIMIT/GOMAXPROCS decision anywhere, and runtime metrics aren't even collected
**Evidence:** zero hits for `GOGC|GOMEMLIMIT|SetGCPercent|SetMemoryLimit|GOMAXPROCS|automaxprocs` in the tree; no resource limits to anchor them (GAP-2); the stress scrape set collects no `go_gc_*`/`runtime/metrics` series (nothing in `test/stress/` or optimizations docs). Round-2 burst forensics observed ~16 GCs/s (per investigation notes) — at GOGC=100 with a small live heap and 400-worker allocation churn, the collector runs continuously; GC assists land directly in watch-decode and reconcile latency, i.e., in S1/S2 of the ROUND7 budget. At 10k+ cached objects per shard (dimension: informer memory) the live heap grows 10-50×, changing GC cadence again — unprofiled.
**Why it matters:** at sub-100ms targets, GC assist/pause jitter is a real p99 term; at 1000/s the allocation rate scales linearly. This is the cheapest unexplored knob class left on the controller side. (sync.Pool: no usage in tree; defer until an allocs profile from a clean leg (GAP-1) shows a hot site — rawpatch and CBOR already removed the two known ones.)
**Impact class:** tail at burst; p90 at sustained rates. **Effort:** S — set `GOMEMLIMIT` = ~80% of a real memory request (GAP-2) + A/B `GOGC=200/400`; add `runtime/metrics` to the bench scrape set permanently.
**ROUND7 ordering:** ride along with gate zero's clean leg (GAP-1) — same cluster, one extra env var per leg.

### GAP-8 — The sandbox metrics collector walks the entire sandbox cache on every /metrics scrape
**Evidence:** `RegisterSandboxCollector` registers a collector whose `Collect` does a full cache `List` of ALL sandboxes per scrape (`internal/metrics/sandbox_collector.go:97-105`; the code's own comment concedes "A GaugeVec updated in the Reconcile loop would be more performant (O(1) per scrape)"). `UnsafeDisableDeepCopy` avoids copies but each scrape still iterates every object under the indexer's read lock. The bench scrapes controller metrics continuously (`metrics.jsonl.gz` throughout runs); production Prometheus every 15-30s.
**Why it matters:** O(N) per scrape × N=10k-60k live sandboxes at 500-1000/s = a periodic multi-ms cache-lock/CPU spike synchronized with... whatever the scraper's phase is — a stealth tail-jitter source *inside the latency window*, and it grows with exactly the scale we're targeting.
**Impact class:** tail at 500-1000/s (nil at 300-burst with 600 objects — which is why no round saw it). **Effort:** S (move to reconcile-maintained GaugeVec, as the comment already proposes).
**ROUND7 ordering:** none; hygiene alongside item 5.

### GAP-9 — Crash-recovery at scale: 15s leaderless + one giant unpaginated relist + catch-up storm, never measured; standby-warmth of `replicas: 2` unverified
**Evidence:** Task 13 fixed *graceful* handover (≤2s) and audited restart **correctness** at N=50. Nobody measured *crash* recovery at scale: lease expiry (default LeaseDuration 15s — `mgrOpts` sets no timings, `main.go:406-421`) + reflector re-LIST of every watched resource. At RV="0" the reflector list is served from the watch cache as **one unpaginated response per resource** — at 10k sandboxes + 10k pods + 10k claims that's a multi-hundred-MB decode/alloc burst (interacting with GAP-7's GC) followed by initial-sync enqueue of *every* object while 15s × rate (15k claims at 1000/s) of backlog is also arriving. ROUND7's dead-end rejected WatchList **for hot-path latency** and explicitly said restart behavior "is not the bottleneck" — that judgment was made without ever measuring recovery time at scale; this gap is the measurement, not a relitigation. Also unverified: whether a standby replica (`replicas: 2`, PDF p. 11) has warm informers pre-election or starts its caches only after winning the lease — if the latter, the second replica buys lease-wait only, not relist time.
**Why it matters:** at 1000/s, every second of recovery is 1000 claims of SLO breach; "how long until p90 recovers after a controller OOM-kill at sustained 500/s" is the first question a production review asks and we have no number.
**Impact class:** robustness. **Effort:** S-M (one chaos leg in the sustained phase: `kubectl delete pod` the leader, measure claim-latency recovery curve + relist bytes; then decide on WatchList flags/standby topology with data).
**ROUND7 ordering:** add to item 6's benchmark matrix (sharding legs already build the multi-replica topology this needs).

### GAP-10 — Leader-election renewals ride the saturated write shards, unmonitored
**Evidence:** the sharded round-robin transport is installed via `cfg.WrapTransport`, which leader election picks up (`transport.go:104-113` comment states so); APF-side the lease writes are protected (critical PL includes coordination leases) but **client-side** renewals queue behind the same in-flight write storm that round-2 measured inflating RTTs 3-5× (and worse regimes are exactly what 1000/s tests will create). Default RenewDeadline 10s gives margin, but nothing scrapes `leader_election_master_status`/renew latency, so a near-miss (renew succeeding at 8s under saturation) is invisible until it becomes a leadership flap mid-burst — which, combined with GAP-9, is the worst-case cascade.
**Impact class:** robustness at 500-1000/s. **Effort:** S (add LE metrics to the scrape set; if data shows drift, give LE the same dedicated-connection treatment as `--separate-watch-connection` — a 10-line variant of `newIsolatedHTTPClient`).
**ROUND7 ordering:** none; measurement rider on gate zero.

### GAP-11 — Connection lifecycle: lazy dials, no TLS session resumption, no pre-warm, and zero network-level chaos testing of the transport stack
**Evidence:** shard transports and the isolated watch client dial lazily on first use (`transport.go` builds transports; nothing issues a warm-up request); client-go's tls.Config has no `ClientSessionCache`, so every re-dial is a full handshake + cert verification. After deploy/failover, the first request on each of N shards pays TCP+TLS+HTTP/2-settings on the latency path. The custom stack (round-robin shards + isolated watch connection) has never seen a network fault: a half-dead watch connection stalls all informers until HTTP/2 ping health-check fires (client-go defaults ReadIdleTimeout≈30s — worth a unit test proving `rest.TransportFor`-built shards actually inherit it, since a silent 30-45s informer stall at 1000/s is 30-45k claims). Round-robin is also load-oblivious: a degraded shard keeps receiving 1/N of traffic including lease renewals (GAP-10).
**Why it matters:** mostly failover/rollout tail and silent-degradation robustness; the single-IP kops CP makes today benign, but the L4 multi-apiserver plan multiplies connection count and failure modes.
**Impact class:** robustness + failover tail. **Effort:** S (startup pre-warm: one `/version` GET per shard before readiness; unit-test h2 ping inheritance; optional ClientSessionCache) + the chaos leg shared with GAP-9.
**ROUND7 ordering:** none.

### GAP-12 — Claim-status payload duplication: the byte audit (SCALING-GUIDE idea D) stops at pod specs; claim/watch-event bytes are the ones that multiply
**Evidence:** the claim's Ready write embeds forwarded sandbox status (name, podIPs, conditions — `sandbox_client`/`k8s_helper` read exactly name+Ready+podIPs); idea D audits *pod spec* size against the ≤10KB budget and "Sandbox/SandboxClaim encoded sizes" as informational. What no one scoped: the **claim status PATCH is the single in-window write** post-L1, and its bytes are paid again per watcher per event (controller + every SDK waiter, GAP-5) at S3+S4 — the two segments the ROUND7 budget shows dominating. If forwarded status carries more than the SDK-consumed triple (extra conditions, serviceFQDN, full SandboxStatus copy), trimming it is a multiplicative S3/S4/etcd win that CBOR then compounds.
**Impact class:** latency-p50/p90 (small, floor-adjacent) + churn bytes at rate. **Effort:** S (extend the gate-zero audit: `kubectl get -o json | wc -c` per object + bytes/event from the watch stream; trim only with data). Condition-churn side checked and clear: `updateStatus` DeepEqual short-circuits and `lastWrittenStatuses` suppresses echoes — no periodic no-op write pattern found.
**ROUND7 ordering:** folds into item 3/4's measurement work.
